Milliy Ecom (v1)

Ecom API — сервис интеграции биллингов клиентов с эквайрингом банка

Обязательные заголовки запроса
Каждый запрос к API должен содержать следующие HTTP-заголовки:

X-API-KEY — публичный ключ клиента, предоставляемый системой
X-SIGNATURE — криптографическая подпись запроса
X-TIMESTAMP — временная метка запроса (Unix timestamp)
X-REQUEST-ID — уникальный идентификатор запроса

Получение ключей
Каждому клиенту выдаются два ключа:

API-KEY — используется для идентификации клиента
SECRET-KEY — используется для генерации подписи запроса (должен храниться в секрете и не передаваться в API запросах)

Генерация подписи (X-SIGNATURE)
Подпись запроса формируется с использованием алгоритма HMAC (Hash-based Message Authentication Code).

Алгоритм генерации:
Формируется строка для подписи:
X-TIMESTAMP + '.' + request_body

Полученная строка подписывается с использованием SECRET_KEY и алгоритма HMAC (SHA256):
X-SIGNATURE = HMAC_SHA256(SECRET_KEY, X-TIMESTAMP + '.' + request_body) (Для GET-запросов поле request_body должно быть пустой строкой: request_body = "")

Важно
• X-TIMESTAMP должен быть актуальным (±1 минута)
• X-REQUEST-ID должен быть уникальным для каждого запроса
• Любое изменение body или timestamp делает подпись недействительной
• SECRET_KEY никогда не должен передаваться клиенту или в API запросах.

Структура ответа API

Все ответы API возвращаются в едином формате:

{
  "status": {
    "code": 0,
    "message": "OK"
  },
  "data": {},
  "meta": {
    "request_id": "11744053-78fe-4d07-a23a-0e49c5247363",
    "timestamp": 1777015488
  }
}

Поле Тип Описание
status.code integer Код результата операции. (0 - Success)
status.message string Описание результата операции
data object Основные данные ответа. Структура зависит от endpoint-а
meta.request_id string Уникальный идентификатор запроса, передаваемый в HTTP header X-REQUEST-ID. Формат значения: string (рекомендуется UUID)
meta.timestamp integer Unix timestamp времени ответа

Получить токен доступа

Шифрование учетных данных (RSA 2048 with PKCS#1 v1.5 padding)
Для обеспечения безопасности передаваемых данных, такие как username и password, используются алгоритмы асимметричного шифрования на основе RSA с длиной ключа 2048 бит.

Как это работает
- Перед отправкой на сервер значения username и password шифруются на стороне клиента.
- Для шифрования используется публичный RSA-ключ (RSA Public Key, 2048 bit), получаемый через метод /auth/token/public-key, предоставляемый системой.
- После шифрования данные преобразуются в зашифрованный формат (ciphertext), который безопасно передается по сети.
- На стороне сервера данные расшифровываются с использованием приватного RSA-ключа (Private Key).

Платежи

Одноэтапный платеж

Одноэтапный платёж — это сценарий оплаты, при котором подтверждение карты и списание средств происходят в рамках одной операции практически одновременно.

Например, при покупке электронных билетов оплата выполняется сразу после ввода платёжных данных. После успешного завершения операции клиент получает оплаченный товар или услугу в кратчайшие сроки с учётом времени обработки со стороны сервиса.

Особенности:

  • После успешной оплаты callbackUrl получит уведомление с purpose = ONE_TIME_PAYMENT.
  • Сессия автоматически истекает по истечении sessionTimeout секунд.

Процесс оплаты:
  • Отправьте запрос → получите transactionId и paymentUrl.
  • Перенаправьте клиента на paymentUrl.
  • Клиент вводит данные карты и подтверждает оплату.
  • После завершения клиент возвращается на successUrl или failureUrl.
  • Ваша система получает итоговое уведомление через callbackUrl.

Рекуррентного платежа (подписка)

Рекуррентный платёж — это автоматическое списание средств с карты клиента через определённые промежутки времени (подписка).

Особенности:

  • Период задаётся в формате Cron. Минимальный интервал — 1 день.
  • Первый платёж выполняется вручную (клиент вводит карту) — это инициализация привязки.
  • Последующие платежи происходят автоматически согласно расписанию.
  • При неудачном списании подписка переходит в статус FAILED без повторных попыток.
  • После инициализации через callbackUrl придёт purpose = RECURRING_PAYMENT.
  • При каждом автосписании через callbackUrl придёт purpose = SUBSCRIPTION.

Cron формат (примеры):
  • 0 0 1 * * — 1-го числа каждого месяца
  • 0 9 * * 1 — каждый понедельник в 09:00
  • 0 0 */7 * * — каждые 7 дней

Процесс оплаты:
  1. Отправьте запрос → получите transactionId, subscriptionId и paymentUrl.
  2. Перенаправьте клиента на paymentUrl для ввода данных карты.
  3. После завершения клиент возвращается на successUrl или failureUrl.
  4. Ваша система получает уведомление через callbackUrl.
  5. Последующие списания происходят автоматически по расписанию Cron.

Привязка карты

Привязка карты — сохранение платёжных данных клиента для последующих оплат без повторного ввода реквизитов.

Особенности:

  • Списание средств не производится — только сохранение карты.
  • После успешной привязки через callbackUrl придёт purpose = CARD_BINDING с cardToken.
  • Полученный cardToken используйте для последующих платежей без ввода карты.
  • Обязательно передавайте clientId для корректной привязки к аккаунту.

Процесс привязки:
  1. Отправьте запрос → получите transactionId и paymentUrl.
  2. Перенаправьте клиента на paymentUrl для ввода данных карты.
  3. Клиент вводит реквизиты карты и подтверждает привязку.
  4. После завершения клиент возвращается на successUrl или failureUrl.
  5. Ваша система получает cardToken через callbackUrl.

Отвязка карты

Отвязка карты — удаление ранее сохранённых платёжных данных клиента.

Особенности:

  • Списание средств не производится — только удаление привязанной карты.
  • Используйте cardToken, полученный ранее при привязке карты (purpose = CARD_BINDING).
  • Обязательно передавайте clientId для корректной идентификации владельца карты.
  • После успешной отвязки карта становится недействительной для последующих платежей.

Процесс отвязки:
  1. Отправьте запрос с clientId и cardToken.
  2. Система проверяет принадлежность карты клиенту.
  3. Привязка карты удаляется.
  4. В ответе возвращается результат операции.

Списание с привязанной карты

Списание с привязанной карты — одноэтапное списание средств с карты клиента по сохранённому токену без повторного ввода данных карты.

Особенности:

  • Требуется cardToken, полученный через /payment/bind.
  • Списание происходит мгновенно — страница оплаты не открывается.

Пополнение карты (Credit) — это перевод (выплата) средств на карту клиента.

  2. В ответе получите transactionId и статус транзакции.
  3. Итоговый результат обработки придёт в вашу систему через callbackUrl.

Callback по статусу операции

Пример callback уведомления Webhook

Callback URL используется для получения уведомлений о статусах операций.

На указанный URL система отправляет HTTP POST запросы с информацией о событиях.

Требования к Callback URL:

  • Метод: POST
  • Аутентификация: Basic Auth (username и password)
  • Формат данных: JSON

Retry-логика при недоступности URL:

Если запрос не был успешно доставлен (нет ответа или ошибка), система выполняет повторные попытки отправки по следующему графику:

  • 1-я попытка — через 30 секунд
  • 2-я попытка — через 2 минуты
  • 3-я попытка — через 10 минут
  • 4-я попытка — через 1 час
  • 5-я попытка — через 6 часов

Все попытки выполняются автоматически. После исчерпания всех попыток доставка считается неуспешной.

Важно:

URL для callback должен быть предоставлен банку и предварительно согласован.

Лимиты мерчанта

Лимиты мерчанта — это ограничения на суммы операций, устанавливаемые для каждого мерчанта индивидуально.

На какие операции распространяются лимиты:

  • CREDIT — пополнение карты (выплата средств)
  • DEBIT — списание средств с карты

Лимиты для CREDIT и DEBIT устанавливаются отдельно и не зависят друг от друга.

Привязка к валюте:

Лимиты задаются отдельно для каждой валюты. Например, лимиты для операций в UZS и USD считаются независимо друг от друга.

Виды лимитов:

  • Разовый (one-time) — максимальная сумма одной операции
  • Дневной (daily) — суммарный объём операций за календарный день
  • Недельный (weekly) — суммарный объём операций за календарную неделю
  • Месячный (monthly) — суммарный объём операций за календарный месяц
  • Годовой (yearly) — суммарный объём операций за календарный год

Как работает проверка:

При каждой операции система проверяет все виды лимитов. Операция будет отклонена, если её сумма превышает разовый лимит, либо если сумма операции вместе с уже проведёнными операциями за период превышает соответствующий периодический лимит.

Коды ошибок:

  • 3022 — лимиты для данного мерчанта, типа операции и валюты не установлены. Для настройки лимитов обратитесь в банк.
  • 3023 — операция отклонена: превышен лимит (разовый или один из периодических).

Важно:

Значения лимитов устанавливаются и изменяются банком. Для увеличения лимитов обратитесь в банк.
